## 二、先补一件最重要的东西：给项目一个业务约束

CRUD API 是最难练架构的题目，因为它没有约束，也就没有取舍。
先给它编一个真实场景（写进 README 的"业务背景"）：

> 团队协作看板。1 万注册用户，500 日活，日增 2 万任务。
> 峰值：读 200 QPS、写 20 QPS。P99 < 150ms。可用性 99.9%。
> 数据保留 1 年。单机 2C4G 的云主机预算。

然后每个技术决策都必须能回答："我是为了满足哪一条质量属性，才这么做的？"

**质量属性场景模板（每条非功能需求都这么写）：**

| 字段 | 示例 |
| --- | --- |
| 来源 | 看板用户 |
| 刺激 | 打开任务列表 |
| 环境 | 早高峰，读 200 QPS |
| 制品 | `GET /api/v1/tasks` |
| 响应 | 返回第一页 10 条 |
| 度量 | P99 < 150ms，错误率 < 0.1% |

写 6~8 条，放进 `docs/quality-attributes.md`。这是后面所有设计和压测的靶子。

## 三、六周计划（2026-11-09 起，每周约 10 小时）

### W1（11/09–11/15）收尾：让它可追溯、可演示

| 任务 | 产出 |
| --- | --- |
| `git init` + 首次提交 + `.gitignore` 复查 | 一个干净的仓库 |
| 补 3 份 ADR（决策早就做了，现在补记录） | `docs/adr/` 三份 |
| 画 C4 Context / Container 图（Mermaid 即可） | `docs/architecture/c4.md` |
| 修 3 个技术债：`ORDER BY`、`PUT→PATCH`、`created_at/updated_at` | 代码提交 |
| 可选进阶：Alembic 首次迁移，替掉 `create_all` | `alembic/` |

**ADR-001 为什么先用 SQLite**（不是"方便"，要写清楚：单机、读多写少、零运维、
并发写是唯一风险、迁移成本被 repository 层隔离）
**ADR-002 为什么先做单体**（团队 1 人、无独立扩容需求、部署简单、
过早拆分会把分布式复杂度提前引入）
**ADR-003 为什么分层 + repository 返回 dict 而不是 ORM 对象**
（隔离 ORM，代价是手工映射，容易漏字段——这就是权衡）

> 验收：换一台机器，`git clone` → `pip install -r requirements.txt` → `pytest` 全绿 → 起服务能用。

### W2（11/16–11/22）契约与可观测性

- 统一错误响应体：`{"code", "message", "details", "request_id"}`
- 领域异常 `TaskNotFound`：**service 层不再 `import HTTPException`**，
  由 api 层统一映射成状态码（现在 `task_services.py:1` 是分层泄漏）
- `request-id` 中间件 + JSON 结构化日志
- `/health/live`（进程活着）与 `/health/ready`（DB 可用）拆开
- 一个最小指标端点（QPS / P95 / 错误率）
- **验收：能凭日志和指标，定位一次慢请求慢在哪一层**

### W3（11/23–11/29）容器化 + 换 Postgres

- 配置外置：`pydantic-settings` + `DATABASE_URL` 环境变量（现在是硬编码 `app/database.py:4`）
- `Dockerfile` + `docker-compose.yml`（app + postgres，带 volume）
- 容器启动时跑迁移
- 同一套测试跑在 Postgres 上
- **ADR-004：为什么现在换 PG？迁移代价多少？**（连接池、事务、并发写、类型差异）
- **验收：`docker compose up` 一条命令起全栈，重启后数据还在**

> 这一步是全程最有价值的一步：它检验"你的分层到底有没有把存储隔离干净"。
> 如果换库时改了 api 层或 service 层，说明分层是假的。

### W4（11/30–12/06）压测与容量

- k6 或 locust 脚本：读多写少，阶梯加压（10→50→100→200 QPS）
- 找瓶颈：SQLite 写锁、连接池、缺索引、N+1、GC
- 报告：QPS / P99 / 错误率 / CPU / 内存
- **ADR-005：连接池大小怎么定（为什么不是越大越好）**
- **验收：能说出"2C4G 上这个 API 的容量上限是 X，瓶颈是 Y，再往上要先改 Z"**

### W5（12/07–12/13）故障演练与演进设计（只设计，不实现）

- 演练：DB 挂掉、慢查询、并发写冲突、磁盘写满
- 每次演练写复盘：时间线 / 根因 / 影响 / 改进项
- 演进设计（画图 + ADR-006，可以不写代码）：
  - 加 Redis 缓存：穿透 / 击穿 / 雪崩怎么防？一致性怎么保证（删缓存 vs 更新缓存）
  - 异步统计：为什么必须异步？消息丢失怎么办（Outbox）？
  - 限流 / 降级 / 熔断：限谁的流？降级后返回什么？
  - 读写分离 / 分库分表：分片键选什么？跨片查询怎么办？
- **验收：能讲清"流量涨 10 倍，我改哪里，代价是什么，什么时候才值得改"**

### W6（12/14–12/20）评审与输出

- 对着一份"架构评审 10 问"讲 30 分钟（不看稿）
- 写一篇复盘博客 / 一份完整架构文档
- README 改写成可交付的项目文档
- 定下一个项目（见第五节）

**每周固定节奏：**

| 频率 | 动作 |
| --- | --- |
| 每天 | 30min 读书/读源码 + 60min 写代码 + 15min 写笔记 |
| 每周日 | 30min 复盘：这周做了什么决策？代价是什么？下周改什么？ |

## 四、整体学习内容（能力地图）

架构能力 = 技术判断力 + 业务抽象力 + 权衡决策力 + 落地推动力。
下面七块是内容清单，**不用按顺序全学**，跟着项目需要走。

### 1. 代码与分层（现在就在练）

- 分层边界：谁可以依赖谁，为什么 service 不能依赖 HTTP 框架
- 依赖倒置、接口隔离、repository 的存在意义（可替换存储）
- SOLID、贫血模型 vs 充血模型
- 模块化单体（modular monolith）：一个部署单元，内部强边界
- **练习点**：把 `HTTPException` 从 service 移走；给 repository 抽接口

### 2. 数据（最容易被低估的一块）

- 索引原理（B+ 树、联合索引最左前缀、覆盖索引）
- 事务与隔离级别（读已提交 / 可重复读 / 幻读）
- 连接池、N+1、慢查询分析（EXPLAIN）
- 迁移（Alembic）、零停机变更（加列、回填、双写）
- CAP 的真实含义（P 不是可选项）、BASE、最终一致
- **练习点**：给 `created_at` 建索引，用 `EXPLAIN` 看执行计划变化

### 3. 分布式与一致性（第二个项目再上）

- 幂等：幂等键、去重表、唯一索引兜底
- 重试与退避、超时传递、熔断、限流、隔离舱
- 消息队列语义（至少一次 / 至多一次 / 恰好一次是伪命题）
- Outbox、Saga、TCC、本地消息表
- 分布式 ID（号段 / 雪花）、分布式锁的真实用途
- **练习点**：给"创建任务"加幂等键，思考重复提交会怎样

### 4. 非功能与可观测性（W2 开始）

- 质量属性：性能、可用性、可扩展、可维护、安全、成本
- SLO / SLI / 错误预算
- 日志（结构化、采样）、指标（RED / USE）、追踪（trace id 贯穿）
- 容量规划、压测方法论
- 安全：认证授权（OAuth2/JWT）、输入校验、越权、密钥管理
- **练习点**：把 `title` 长度限制加在 schema 层（SQLite 不强制 VARCHAR 长度！）

### 5. 交付与运维（W3 开始）

- 12-Factor App、配置外置、环境一致性
- Docker、compose、镜像分层与体积
- CI/CD：lint + test + build，分支策略
- 蓝绿、金丝雀、功能开关、回滚
- IaC（Terraform）——了解即可，别早学
- **练习点**：写一条 GitHub Actions，PR 时自动跑 pytest

### 6. 领域建模与演进（进阶）

- DDD 战略：限界上下文、上下文映射、事件风暴
- DDD 战术：实体、值对象、聚合、领域事件、仓储
- 演进式架构：适应度函数、绞杀者模式、分支抽象、并行运行
- 契约测试、API 版本化（你现在有 `/api/v1`，想想 v2 怎么发）
- 康威定律：架构和团队结构互相塑造
- **练习点**：给"任务"补一个"归属人/项目"概念，做一次领域建模，看分层怎么变

### 7. 软技能（决定你能不能成为架构师）

- ADR：怎么写、怎么让人愿意读
- 设计文档：背景 / 目标 / 非目标 / 方案 / 备选 / 权衡 / 风险 / 验证
- 架构评审：怎么主持、怎么收集异议
- 成本意识：机器、人力、维护、机会成本
- 向上沟通：把技术风险翻译成业务语言
- **练习点**：每周写 1 份 ADR 或复盘，坚持 12 周

## 七、架构评审 10 问（每次设计完，自问一遍）

1. 解决什么问题？目标与非目标分别是什么？
2. 约束是什么？流量、数据量、延迟、成本、团队规模？
3. 备选方案有哪些？为什么不选它们？
4. 为什么选这个？取舍点在哪？（说不出代价 = 没做权衡）
5. 最坏情况会怎样？怎么缓解？
6. 怎么演进？怎么回滚？
7. 怎么验证它达到了目标？指标是什么？
8. 团队里其他人能维护吗？
9. 引入了哪些新依赖？谁来运维？
10. 三个月后回看，这个决策还可能成立吗？

## 八、当前代码的具体问题清单（按优先级，W1 处理前 5 条）

| 优先级 | 问题 | 位置 | 为什么是问题 | 怎么改 |
| --- | --- | --- | --- | --- |
| P0 | 没有 Git 仓库 | 根目录 | 所有学习成果没有版本保护，一次误删全没 | `git init` + 首次提交 |

| P1 | `PUT` 承担部分更新 | `api/tasks.py:24` | 语义错误，客户端无法区分"没传"和"设为空" | 改 `PATCH` |
